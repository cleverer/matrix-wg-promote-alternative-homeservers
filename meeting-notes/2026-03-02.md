### Policy for the List

- We need to structure the list better. To do so, we want to mentally split the ouput of the working group into two parts:
    - Policy (are for people)
        - Contains the rules for being on the list
        - Contains reasons for being removed off the list
        - Contains an appendix, that lists the data that need to be collected about the servers, and how to collect it (e.g. via a spec for a well-known url)
    - Technical list / table (for client)
        - Specifies the format of the list, how to fetch it, and what data it should contain
        - This is the "trusted servers list" that clients will fetch and use to filter servers. It is generated by the server, but the client can choose which server's.
        - A list can be hosted by any (web)server. It doesn't have to be a homeserver itself, but it can be.
        - The idea is that a client developer hosts it's own list or uses the one of the matrix foundation.
        - The format of the list should be specified as an MSC as well as the recommended rules of selectiong a Homeserver from the list.
        - For now, we chose not do do a "Web-of-Trust": a server calculates the list and not clients
            - Decentralized list calculation will be left as an exercise to the intern(et) ;)

We went through the PRs:
- A very important point is that the rules are mainly for basic users that have no technical knowledge. Hence, the rules do not need to cater to technical users, but should be simple and easy to understand for everyone.
- It is also important, that the policy is specifically for the list for the matrix foundation, and not for any other list. Any other server or list may have their own rules.
- In contrast the technical specification needs to be implemented by any server and client the same way. but it just allows to fetch recommended servers in a standard fashion and allows the homeserver selection to feel familiar accross clients.
